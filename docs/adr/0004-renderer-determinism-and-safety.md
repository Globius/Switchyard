# 0004. The renderer is deterministic, validated by real binaries, and rejects unsafe values

Status: Accepted
Date: 2026-10-10

## Context

The renderer turns tenant-controlled data into configuration for a process that runs as a gateway
for many tenants. The design requires: the same state gives the same bytes (so a hash can detect
drift), user values are validated and escaped, and rendered output is checked by the real binary.

## Decision

**Determinism**

- `render_haproxy(snapshot, se_group_id)` is a pure function. It reads no clock, environment,
  randomness or network, and the output contains no timestamps or ids.
- Everything is sorted: services and backends by name, servers by server name, SNI lists, map lines
  and allow-list networks by key. Input order (tuple order, database row order) cannot change the
  output; a test shuffles every collection and compares.
- `RenderResult.content_hash` is a SHA-256 over sorted `(path, content)` pairs. Later milestones
  store it per deployment and compare it with what an SE reports.
- Output uses LF endings and ends with a newline.

**Safety**

- Two guards, as the design requires. The domain validators (`domain/validators.py`) restrict every
  user value to a conservative alphabet when the object is created. The renderer
  (`render/escape.py`) checks again before interpolating and **rejects** a value that does not fit
  rather than quoting or repairing it, because a silently altered config is worse than a failed
  render.
- The alphabets exclude whitespace, quotes, backslash, `#`, `$`, braces and control characters.
  `%` in redirect locations is doubled, because HAProxy reads `%` in log-format strings.
- Regexes are generated by the renderer from validated hostnames, never accepted from users. They
  avoid backslashes (`[.]`) and are single-quoted in the config.
- There are no free-form config snippets in phase 1.
- Injection tests build objects with `model_construct` (bypassing validation) and assert the
  renderer still refuses them.
- Validation always runs first: `render_haproxy` slices the snapshot to the SE group and calls
  `ensure_valid`, so rules such as SAN coverage and VIP placement hold at render time as well.

**Verification by real software**

- Every golden case (`tests/golden/<case>/input.yaml` → `expected/`) must pass `haproxy -c` in the
  `haproxy:3.2` image with no warnings (`tests/integration/test_golden_haproxy.py`). Files are copied
  into the container through the Docker API, so this works on Windows, WSL2, Linux and
  Docker-in-Docker CI.
- A behaviour suite sends requests through a rendered config on a throwaway Docker network and
  checks what backends receive (`tests/integration/test_haproxy_behavior.py`). `haproxy -c` cannot
  catch semantic mistakes such as an unguarded map lookup or a missing `option forwardfor`; this
  suite found both.
- `UPDATE_GOLDEN=1 pytest tests/unit/render` rewrites expected files after an intentional change; the
  diff is then reviewed like code.

## Consequences

- A render can fail on data that was valid when stored if the validators tighten later. That is
  deliberate: the failure is reported before anything reaches an SE.
- Certificates and keys are never rendered. `crt-list` entries point to
  `/etc/switchyard/certs/<name>.pem`, which the agent writes from OpenBao. Validation therefore uses
  throwaway self-signed certificates.
- Changing any output byte shows up as a golden-file diff in review.

## Alternatives considered

- **Jinja2 with autoescape or custom quoting filters only.** Quoting cannot make arbitrary text safe
  across HAProxy's several parsing contexts (config words, ACL arguments, log-format strings).
- **Build the config through the Data Plane API object by object.** The design pushes the whole
  `haproxy.cfg` through the raw endpoint so one hash describes one state.
