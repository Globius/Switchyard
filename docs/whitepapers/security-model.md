# Security model

What Switchyard protects, against whom, and how. The detailed reviews are in [security/backend-review.md](../security/backend-review.md)
and [security/ui-review.md](../security/ui-review.md); hardening decisions in ADRs
[0072](../adr/0072-hardening-engines-logins-secrets.md), [0074](../adr/0074-agent-bundle-binding.md) and
[0075](../adr/0075-deploy-hardening.md).

## Threats we design for

1. **A tenant reaching another tenant**: reading its objects, logs, metrics or secrets, or affecting its traffic.
2. **A tenant reaching the platform**: turning configuration input into code or commands on an engine, or into requests
   to internal systems.
3. **A compromised or rogue network peer**: someone who can reach an engine's management address or replay old traffic.
4. **Credential theft**: keys and passwords leaking through the database, logs, backups, Git or the API.
5. **An operator mistake** that takes every engine down at once.

## Principles

**Tenancy is enforced twice.** The service layer checks the caller's role for the tenant on every call, and PostgreSQL
row-level security filters every tenant table by the session's tenant. Application code never disables RLS; administration
uses a separate database role. A bug in one layer is caught by the other. See [Multi-tenancy](multi-tenancy.md).

**No free-form configuration.** Tenants describe intent with typed fields. Every value that reaches a configuration file
(host names, paths, header names and values, regexes, cookie names, media types, Lua constants) passes a strict validator,
and the renderer escapes it again. There are no snippets, no custom WAF rules, no external health-check scripts, and no
tenant-supplied Lua. Response bodies are served as files and never evaluated.

**No secrets at rest outside OpenBao.** PostgreSQL, logs, fixtures and the Git mirror hold only `secret_ref`s (OpenBao paths).
A tenant may reference only its own namespace (`kv/tenants/<tenant>/...`) and operator-declared shared prefixes. The
controller's OpenBao token gets a policy generated by `syctl openbao-policy`, so a code bug cannot widen what it reads.
Private keys reach an engine only inside the Data Plane API certificate push or a signed agent bundle.

**Engines take orders from one place, in a narrow form.**

- The controller talks to engines over mTLS only: the Data Plane API and `sy-agent`. There is no SSH from the controller and
  no remote shell or command endpoint on the agent.
- The agent writes only under `/etc/switchyard/` and reloads only an allowlisted set of units. It has no endpoint that reads
  files back.
- Bundles are signed (Ed25519), bound to one engine by name, and carry a strictly rising sequence, so a bundle cannot be
  replayed or redirected to another engine. `-controller-cn` limits which client certificate may call the agent.
- Agent certificates come from an OpenBao PKI, short-lived (7 days) and renewed every 8 hours; enrolment uses one-time tokens.

**Outbound requests are fenced.** Alert webhooks, JWKS URLs, Kubernetes API servers, DNS servers and IP-list feeds are
checked when saved and again at use: https only, no credentials in URLs, no private or loopback targets unless the operator
allows the range, no redirects followed, size limits. IP-list and geo sources are the operator's, never a tenant's URL.

**Deploys cannot copy another tenant's engine.** Only guests flagged as Proxmox templates are cloned, node and pool names are
validated, and engine and VIP addresses cannot collide.

**Changes are gradual and recorded.** Every apply goes canary first, then rollout; drift is reported, not overwritten. Every
change, sign-in, approval and export is an audit event, and an audit export is itself audited.

## People and machines

- Sign-in through OIDC or SAML (signed assertions only, replay-protected); roles come from identity-provider groups mapped per
  tenant. API tokens are scoped to a tenant or the system and expire.
- Break-glass is a local account with TOTP, off by default, enabled for a reason and a time window, and throttled per source.
- Failed sign-ins are throttled per source address and per account from that address, so a stranger cannot lock the real
  administrator out.
- The UI proxy sets a strict CSP, HSTS, `nosniff` and `frame-ancestors 'none'`, and rate-limits login endpoints.

## Protecting tenants' applications

Engines also enforce tenant security policy at the edge: TLS profiles and mTLS, allow and deny lists (including country and
reputation feeds), rate limits, the Coraza WAF with a pinned OWASP CRS, bot and connection-flood protection with a JavaScript
challenge or CAPTCHA, OIDC login with group rules and device posture, JWT validation and client-certificate identity. All of
it runs on the engine, so it keeps working when the controller is down. The login sidecar fails closed; the WAF's failure mode
is the tenant's explicit choice. See the [feature notes](../features/index.md).

## Out of scope

Volumetric DDoS (handled upstream), endpoint-agent device posture, per-user session revocation for edge logins, and the
security of the Proxmox hosts and networks themselves.
